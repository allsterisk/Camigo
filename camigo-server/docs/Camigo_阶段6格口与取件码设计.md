# Camigo 阶段6：格口与取件码设计

## 1. 依据与边界

本阶段唯一业务依据为 `修改意见_最终执行版.md` 的“阶段6：格口、取件码和取件闭环”。阶段5到达目的地后，订单停留在 `ARRIVED`、包裹停留在 `DELIVERING`；阶段6由配送员选择兼容格口完成入柜，再由包裹所有者凭四位取件码完成取件。

格口容量按 `S < M < L < XL` 排序。包裹可以放入同尺寸或更大格口，不能放入更小格口。前端仅展示兼容且可用的格口，后端仍在事务和行锁内再次校验，不能依赖前端选择结果。

## 2. 数据模型与索引

`storage_records` 新增 `pickup_code CHAR(4) NULL`，并增加唯一索引 `uk_storage_active_pickup_code`。取件码以字符串保存，因此 `0000` 等前导零不会丢失；取件完成后立即置空。

继续使用以下数据库约束阻止并发重复占用：

- `uk_storage_active_slot(active_slot_id)`：同一格口最多一条活动存放记录；
- `uk_storage_active_parcel(active_parcel_id)`：同一包裹最多一条活动存放记录；
- `uk_storage_active_pickup_code(pickup_code)`：所有非空取件码唯一；
- `idx_locker_slots_compatible(locker_id, status, size_class, id)`：支持兼容格口查询。

历史字段 `pickup_code_hash`、`code_expire_time`、`pickup_records.appointment_id` 以及预约表暂时保留。现有数据库含历史记录，依据“不清理现有数据”的要求，本阶段停用新预约和二维码流程，但不删除历史结构或历史数据。

## 3. 接口

| 方法 | 路径 | 角色 | 作用 |
| --- | --- | --- | --- |
| `GET` | `/api/courier-execution/orders/{orderId}/locker-slots` | `COURIER` | 查询目标柜中兼容且可用的格口 |
| `POST` | `/api/courier-execution/orders/{orderId}/storage` | `COURIER` | 选择格口并完成入柜 |
| `GET` | `/api/parcels/{parcelId}/pickup-access` | `USER` | 包裹所有者查看取件码和格口信息 |
| `POST` | `/api/lockers/pickup` | `USER` | 包裹所有者输入四位取件码完成取件 |

配送员入柜响应只返回格口、订单、包裹和路线结果，不返回取件码。取件码只在包裹所有者的详情接口和页面中展示。

## 4. 入柜事务

入柜统一按“配送订单 → 配送员 → 包裹 → 格口 → 存放记录”的顺序加锁并校验：

- 当前用户确为订单分配的配送员；
- 订单已经到达目的地，且目的地、目标柜和配送员当前位置一致；
- 包裹仍为配送中，尚无活动存放记录；
- 选择的格口属于目标柜、状态可用，且尺寸能够容纳包裹；
- 最新送达节点仍处于 `ARRIVED`，不能重复完成。

后端使用安全随机数生成 `0000` 至 `9999` 的四位字符串；若唯一索引检测到碰撞，仅重新生成取件码并重试，其他并发冲突直接返回业务错误。成功后在同一事务中创建存放记录、占用格口、将包裹更新为 `READY_PICKUP`、将订单和送达节点更新为 `COMPLETED`、更新配送员位置和接单状态，并保存剩余路线版本。任一步失败都会整体回滚，取件码不会生效。

## 5. 取件事务

取件接口按包裹查询并锁定活动存放记录，同时锁定包裹和格口，然后校验用户为包裹所有者、存放记录有效、四位取件码完全一致。成功后立即：

- 将存放记录更新为 `PICKED_UP` 并记录释放时间；
- 将明文取件码和兼容保留的旧哈希字段同时置空；
- 释放格口；
- 写入 `PICKUP_CODE / SUCCESS` 取件记录，`appointment_id` 为空；
- 将包裹更新为 `PICKED_UP`。

所有变化处于同一事务。新流程不创建预约，不接受二维码验证，配送员端也无法读取取件码。

## 6. 前端交互

配送员任务到达后通过格口对话框加载兼容格口、选择并确认入柜；包含加载、空列表、错误、重复提交禁用和窄屏布局。用户包裹详情仅在待取件状态展示四位取件码、柜机和格口信息，并提供取件确认；成功后刷新详情。

页面仅负责组合，格口加载/入柜与取件访问/确认分别由独立组合式函数管理。配送员界面和通用包裹列表均不展示取件码。

## 7. 验证

- 真实 MySQL 集成测试覆盖完整入柜与取件闭环、大包裹拒绝小格口、非空取件码唯一约束、活动格口唯一约束和事务回滚；
- 控制器测试覆盖角色权限、四位码校验、配送员响应不泄露取件码和所有者取件访问；
- 完整后端测试共 35 个测试套件、115 项测试，失败 0、错误 0、跳过 0；
- 前端通过 `vue-tsc` 与 Vite 生产构建，界面规范检测无发现；
- 数据库验收确认活动格口重复组、活动包裹重复组、非空取件码重复组均为 0；
- 阶段前后的 25 条预约和 30 条历史取件记录保持不变，未执行数据清理。

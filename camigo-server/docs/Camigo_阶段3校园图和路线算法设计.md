## 2. 校园图和最短路径

`CampusRouteNetwork` 从有效 `campus_locations` 和有效 `campus_route_edges` 加载图。`bidirectional=1` 的道路作为无向边展开，`DijkstraPathFinder` 计算正权最短路径并返回：

- 总距离（米）；
- 包含起点、途经点和终点的地点编号序列。

应用启动完成时会一次性预热所有有效地点的两两最短路径。地点或道路变化后调用 `invalidate()` 清空图和缓存，下一次查询会重新从数据库加载；也可直接调用 `refresh()` 立即重建。

当前 v16 地图有12个有效地点、14条双向道路，预热结果为144条有向查询缓存。

## 3. 带先取后送约束的最小增量插入

`RouteInsertionPlanner` 接收配送员当前位置、当前未完成节点和新订单的 `PICKUP`/`DROPOFF`：

1. 校验新订单节点类型相同且取件在前；
2. 校验加入后不超过8个活动订单对应的16个未完成节点；
3. 枚举所有取件位置，以及该取件位置之后的所有送达位置；
4. 使用缓存的最短路径计算每个候选序列的总距离；
5. 选择总距离最小的序列，距离相同时按插入位置稳定择优；
6. 返回 `incrementalDistanceMeters`，供阶段4派单评分使用。

路线计算是纯计算，不写数据库。只有配送员接受方案后，阶段4才能调用 `RouteVersionService.saveAcceptedPlan()` 正式保存。

## 4. 行驶时间、操作时间与ETA

参数统一位于 `application.yml` 的 `camigo.routing`：

- 行驶速度：5km/h；
- 服务站基础取件：120秒；
- 每件取件：30秒；
- 目的地基础停靠：30秒；
- 每件选格口并入柜：60秒；
- 最大活动订单：8；
- 算法版本：`dijkstra-insertion-v1`。

每段行驶时间按 `ceil(距离米数 × 3600 / (5 × 1000))` 计算，即文档要求的 `ceil(距离 × 0.72)`。

连续相同地点、相同类型的节点合并为一个操作组：同一服务站只收一次120秒，同一目的地只收一次30秒；每张订单的节点仍单独保存在数据库中，并共享该物理停靠的预计到达时间。

`CURRENT` 是路线版本的位置快照，必须与 `PICKUP`、`DROPOFF` 业务节点分别保存。当前位置与相邻业务节点相同时允许 `location_id` 相同，该段距离和行进时间按0计算；业务节点不会因此自动完成。

## 5. 路线版本和事务一致性

阶段3迁移将旧的 `delivery_order_id`、`route_type`、`start_location_id`、`end_location_id` 改为可空，历史值保持不变；旧 `(delivery_order_id, route_type)` 唯一索引替换为普通兼容查询索引。新版本字段收紧为非空。

保存接受路线时：

1. 锁定配送员行并检查当前位置未变化；
2. 锁定当前活动路线并取得下一版本号；
3. 将旧 `ACTIVE` 路线标记为 `SUPERSEDED`；
4. 插入新 `ACTIVE` 路线；无剩余任务时插入 `COMPLETED` 路线；
5. 插入一个已完成的 `CURRENT` 节点和每张订单独立的待执行节点；
6. 由数据库唯一键兜底保证每名配送员最多一条 `ACTIVE` 路线。

全部操作位于同一事务中，并通过配送员行锁串行化版本号分配。

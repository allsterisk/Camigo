# Camigo 阶段5：配送执行与位置更新设计

## 1. 依据与边界

本阶段唯一业务依据为 `修改意见_最终执行版.md` 的“阶段5：配送执行和位置更新”：登录后强制选择当前位置、取件后更新到服务站、送达时更新到目的地、节点完成后刷新路线，并在配送员端显示地图、箭头和文字路线。

阶段6负责格口占用、取件码和入柜完成。因此阶段5的“确认送达”按“确认到达目的地”实现：配送订单进入 `ARRIVED`，包裹保持 `DELIVERING`，不会提前写入 `COMPLETED` 或 `READY_PICKUP`。

## 2. 接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| `GET` | `/api/couriers/locations` | 查询可选择的有效校园地点 |
| `GET` | `/api/couriers/me/location` | 查询本人位置确认状态 |
| `PUT` | `/api/couriers/me/location` | 确认当前地点并恢复接单状态 |
| `PUT` | `/api/couriers/me/offline` | 退出登录前离线 |
| `GET` | `/api/courier-execution/route` | 查询当前剩余综合路线 |
| `POST` | `/api/courier-execution/orders/{orderId}/pickup` | 按路线顺序确认取件 |
| `POST` | `/api/courier-execution/orders/{orderId}/arrival` | 按路线顺序确认到达目的地 |

位置接口使用文档规定的 `/api/couriers/...` 命名；配送动作集中在 `/api/courier-execution/...`。

## 3. 登录与位置确认

配送员每次登录后先写为 `OFFLINE`，登录响应返回 `locationConfirmed=false`。前端路由守卫只允许其进入位置确认页；确认有效校园地点后，后端在事务中更新：

- `couriers.current_location_id`；
- `couriers.location_update_time`；
- 未满8个活动订单时为 `AVAILABLE`，达到上限时为 `BUSY`；
- 存在活动订单时，以新位置为起点生成新的路线版本。

旧的浏览器会话缺少位置确认字段时默认按未确认处理，避免绕过确认页。

## 4. 配送节点事务

执行取件或到达时统一按“配送订单 → 配送员 → 包裹 → 活动路线/节点”的顺序加行锁，并校验：

- 当前用户确为订单配送员且在职；
- 已确认位置且非离线；
- 订单、包裹状态允许本次动作；
- 当前活动路线包含对应待执行节点；
- 目标节点位于当前路线下一地点，不能跳过节点。

当当前位置已经等于取件点或送达点时，路线仍保存独立的 `CURRENT` 和业务节点，两者可以具有相同的 `location_id`。该相邻路段距离为0；前端可合并地点展示，但 `PICKUP`/`DROPOFF` 仍保持 `PENDING`，只有对应确认接口才能完成。

状态和位置变化如下：

| 动作 | 路线节点 | 配送订单 | 包裹 | 配送员位置 | 路线 |
| --- | --- | --- | --- | --- | --- |
| 确认取件 | `PICKUP: PENDING → COMPLETED` | `ACCEPTED/PICKING_UP → IN_TRANSIT` | 保持 `DELIVERING` | 更新到取件服务站 | 从服务站重算剩余路线并保存新版本 |
| 确认到达 | `DROPOFF: PENDING → ARRIVED` | `IN_TRANSIT → ARRIVED` | 保持 `DELIVERING` | 更新到目的地 | 从目的地重算剩余路线并保存新版本 |

所有变化处于同一数据库事务，任一校验或写入失败都会整体回滚。原有通用订单状态接口不再允许绕过上述执行事务。

## 5. 路线展示

配送员首页和任务页复用 `CourierRoutePanel`，展示用户提供的山东大学软件园校区路线图、当前位置、剩余距离、预计时长、路线版本和分组后的节点顺序。连续位于同一地点的取件/送达任务会合并为一个文字步骤，并以箭头连接。组件包含加载、错误、空路线和窄屏布局。

地图静态资源：`camigo-web/public/images/camigo-campus-route-map.png`。

## 6. 一致性和错误处理

- 未确认位置返回业务错误 `43007`；
- 跳过路线节点、重复执行或路线已变化返回 `43008`；
- 更新使用来源状态条件，阻止并发重复提交；
- 执行动作返回订单状态、包裹状态、当前位置和刷新后的路线，前端随即同步任务和路线；
- 到达目的地不提前执行阶段6的入柜和完成逻辑。

## 7. 验证

- 单元与集成测试覆盖位置确认、取件、到达、路线刷新、权限、登录强制确认和 OpenAPI 注册；
- 真实 MySQL 测试使用事务回滚验证订单、包裹、位置、节点及路线版本的一致性；
- 前端通过 `vue-tsc --noEmit` 和 Vite 生产构建；
- 阶段5界面通过前端规范检测，未发现问题。
